更新日: 2026-09-28 JST

## 1. 目的

本工程表は、`Character Relationship Chart` の VS Code 拡張機能を維持しながら、共通 `core`・共通 UI を利用する独立 Web 版へ段階的に展開するための作業順、依存関係、完了条件、推奨モデル／モードを定める。

工程は意図主導型AI開発（IDAD）に従い、各段階で既存の VS Code 版と Web 版が利用可能な状態を維持する。大きな機能追加や構成変更を一度にまとめず、各段階を独立した完成地点とする。

## 2. 現在地

2026-09-27 時点で第1〜第4段階は完了している。

- 第1段階: UI と VS Code 固有処理の境界を分離
- 第2段階: 共通 `core` を分離
- 第3段階: 読取専用の最小 Web 版を実装
- 第4段階: Web 版で GUI 編集し、編集後の `.jsonc` をダウンロード可能にした
- 第4段階の再検証では、構文検査、通常テスト、DOM 試験、Chromium 実ブラウザ試験、Web 配布物、VSIX の対応を再確認済み
- 第4段階の Web 版は、元ファイルへの直接上書き、`.view.json` の保存、Web 独自 Undo/Redo、ブラウザ永続保存、外部変更との競合管理、SVG 保存にはまだ対応していない

**第5段階は完了（2026-09-28 JST）**。自動試験に加え、利用者の実機で直接保存・再読込と外部変更時の警告・保存停止を確認した。実機の環境詳細や個別結果が未提示の項目は [確認範囲](STAGE5_ACCEPTANCE.md) に残す。次工程は第6段階で、対象ソースに第5段階を反映したことを照合してから開始できる。第6段階の実装にはまだ着手していない。

## 3. 工程設計の原則

1. `.jsonc` と `.view.json` の既存形式を維持する。
2. 人物 ID、複数グループ所属、関係参照、保存済み配置を壊さない。
3. JSONC のコメント・既存整形を、編集対象外まで一括して失わない。
4. VS Code 版の保存、Undo、競合検知、GUI 編集を回帰させない。
5. Web 版で利用者の人物データを外部へ送信しない。
6. Web の直接保存機能を追加しても、第4段階の「編集後ファイルをダウンロードする」経路をフォールバックとして維持する。
7. 外部変更を検出できない状態で元ファイルを自動上書きしない。
8. 本格的なディレクトリ再編は、Web 版の主要機能が固まるまで後回しにする。
9. 各段階で必要なコード変更、回帰テスト、実ブラウザ確認、文書更新、配布物確認までを一つの完了単位とする。
10. `MGMT.md` の `assignment` は実行予定から退避した課題として扱い、本工程表へ自動的には組み込まない。

## 5. 第5段階の設計境界

第5段階では「元ファイルへ直接保存できること」だけを目的にせず、**安全に保存できること**を完了条件とする。

### 含める

- 利用者の明示操作による設定ファイルの保存
- 書込権限の確認
- 保存直前の元ファイル再確認
- 読込時点から外部変更されていた場合の競合検出
- 競合時の上書き停止
- 保存失敗時の編集内容保持
- 非対応環境・権限拒否時の既存ダウンロード方式
- 別設定へ切り替える際の既存破棄確認
- VS Code 版の回帰確認

### 含めない

- `.view.json` の保存
- Web 独自 Undo/Redo
- 自動保存
- ブラウザ保存領域への常時永続化
- ファイルハンドルや権限が次回起動でも必ず維持されることを前提にした設計
- SVG 保存
- 本格的な `packages/`・`apps/` 再編
- `assignment` に退避した機能

この境界により、第5段階だけを完了しても、第4段階と同様に明確な完成地点を保つ。

## 6. 共通の検証方針

各実装段階では、変更箇所に応じて少なくとも以下を確認する。

```sh
npm run check
npm test
npm run test:web
npm run build:web
npm run package
```

必要に応じて次も実行する。

```sh
node --test test/ui-dom-check.js test/web-dom-check.js

```

検証では次を区別して記録する。

- Node.js 上の構文・単体・統合テスト

- 実ブラウザでのファイル選択、編集、保存、ドラッグ、画面表示
- VS Code 模擬 API による回帰
- 実際の Extension Host での確認

- 生成した Web 配布物と VSIX の内容確認

## 8. 工程の見直し条件

次の場合は、後続工程へそのまま進まず工程表を更新する。

- 第5段階で、直接保存と既存のオフライン利用を両立できない重大な制約が確認された

軽微な実装上の調整やテスト追加だけで解決できる場合は、工程を増やさず当該段階の中で処理する。

## 10. 第5段階の実績（2026-09-28 JST）

- 明示的な直接保存、権限要求、保存前と確定直前の生バイト比較、保存後の再読込照合を実装。
- 競合・権限拒否・書込失敗で編集・フォーム・図を保持。結果不明時は直接保存を停止し、ダウンロードへ退避可能。
- `npm test` 96件、共有UI／Web DOM25件、既存ブラウザ8操作群・追加保存UI5操作群に成功。保存成功／競合の自動試験は模擬ハンドルによるもの。
- ネイティブAPIでは実ファイル読込と書込権限拒否時の保護を確認。Headless環境でpickerはAbortError、readwrite権限はdeniedとなり、OS選択・ネイティブ直接保存の成功は未確認。
- 第5段階Web ZIPとVSIXは現行ソースから生成。配布物作成は段階完了を意味しない。
- Dropboxの既存ファイルへ安全に上書きする手段がないため、元ファイルは変更せず、反映用パッケージを提供。適用時は取得時のSHA-256と現在のファイルを比較し、違いがあれば自動上書きしない。
- APIに原子的な比較付き保存はない。最後の比較と確定の間に外部アプリが同時更新する場合の完全排他は未保証。実機確認でもこの制限を説明する。

第6段階への判定: **保留**。実PCの対応ブラウザで `STAGE5_ACCEPTANCE.md` の確認を終え、残る制約を理解したうえで第5段階の完了を記録してから進める。第6段階は、同じ競合保護の制限を前提に `.view.json` を追加する予定であり、今回その実装には着手していない。
